오후 2시 반, 슬랙에 복제 감시 알림이 떴다. "레플리카 복제 적용 에러 47건 증가 — 적용 실패한 트랜잭션이
스킵되면 그 변경분은 영구 유실됩니다. 즉시 확인 필요." 누적 에러 카운터가 9,102에서 9,149로 올라 있었다.
8월에 23시간 동안 주문이 한 건도 안 들어온 장애가 바로 이 카운터에서 시작됐으니, 문구대로라면 비상이었다.

결론부터 말하면 이 장애는 알림이 오기도 전에 스스로 나아 있었다. 그리고 같은 기록 안에,
하루 전부터 28번 경고를 남기고도 아무에게도 도달하지 못한 진짜 위험이 따로 있었다.

## 추적

30분마다 찍는 구독 통계 스냅샷을 보니 카운터가 늘어난 건 30일 동안 딱 한 번, 14:00~14:30 사이였다.
그 뒤로는 9,149에서 멈췄고 수신 지연도 0~30초였다. 계속 죽어 있는 게 아니라 한 번 넘어졌다 일어난 모양이다.

원인은 레플리카 쪽 워치독 기록에 있을 텐데, 그 테이블은 앱을 거쳐야만 볼 수 있었다.
통계 DB에서 바로 읽도록 읽기 전용 외부 테이블을 하나 붙였다. 레플리카에는 아무것도 만들지 않는다.

```sql
import foreign schema public limit to (repl_watchdog_log)
  from server replica_srv into replica_mon;
```

기록은 명확했다.

| 시각 | 판정 | 내용 |
|---|---|---|
| 14:20 | ok | 랙 35kB |
| 14:30 | schema_synced | 원본 설정 테이블에 컬럼 5개 추가 감지 → 레플리카에 자동 추가, worker 재시작 (랙 39MB) |
| 14:40 | ok | 랙 3.6MB, 새 worker 가동 |

원본 쪽에서 예고 없이 컬럼 5개를 추가했고, 논리복제는 DDL을 옮기지 않으니 레플리카 적용이 "없는 컬럼"에서 넘어졌다.
5초 간격 재시도로 47번이면 약 4분이다. 8월에 만든 스키마 자동 추종이 컬럼을 채우자 멈춰 있던 트랜잭션이 재시도로
적용됐다. 스킵이 아니라 재적용이니 유실은 없다. 주문 유입을 10분 단위로 어제와 비교해도 구멍이 없었다.

| 구간 | 오늘 | 어제 |
|---|---|---|
| 14:00 | 140 | 144 |
| 14:10 | 115 | 108 |
| 14:20 | 131 | 122 |
| 14:30 | 124 | 112 |

8월 첫 드리프트 땐 사람이 붙어서 고쳤던 일을, 이번엔 사람 손 없이 10분 만에 끝냈다.

## 진짜 위험은 조용했다

같은 기록을 훑다 이 줄이 눈에 걸렸다.

```
잠재 드리프트 — 타입 불일치·스킵: 메뉴 테이블.플래그 컬럼 pub=varchar(1000) rep=varchar(500)
```

원본은 길이를 1000으로 늘렸는데 레플리카는 500 그대로다. 워치독은 전날 오전 10시 10분부터 이 줄을
**28번** 남겼다. 그런데 화면에만 기록됐지 알림으로는 한 번도 나가지 않았다.

자동 추종은 설계상 컬럼 **추가**만 한다. 타입 변경은 잘못 건드리면 더 큰 사고가 나서 기록만 하도록 했다.
문제는 그 기록이 사람에게 닿지 않았다는 것이다. 원본에 500자를 넘는 값이 하나라도 들어오는 순간 적용이
"value too long"으로 무한히 실패하고, 이번과 달리 자동으로 낫지 않는다. WAL 보존 한도(장애 시 약 6시간)를
넘기면 슬롯이 무효화된다 — 8월 23시간 장애와 같은 길이다.

레플리카에서 길이를 맞췄다. varchar 길이를 늘리는 것은 테이블을 다시 쓰지 않고 정의만 바꾸므로 즉시 끝난다.

```sql
alter table 스키마.메뉴테이블 alter column 플래그컬럼 type varchar(1000);
```

60~70분 주기로 찍히던 경고가 다음 주기(16:20, 16:30)에 사라진 것으로 확인했다.

## 해결: 알림을 "사건"이 아니라 "지금 상태"로 판정

오늘 알림은 두 방향으로 틀렸다. 이미 나은 일에 비상을 걸었고, 살아 있는 위험엔 침묵했다.
에러 증가라는 **사건**만 보고, 지금 어떤 **상태**인지는 안 봤기 때문이다.
감시 함수가 워치독 기록과 worker 상태를 같이 보도록 바꿨다.

| 상황 | 알림 | 빈도 |
|---|---|---|
| 에러 증가 + 최근 40분 내 자동 추종 + worker 가동 + 지연 정상 | ℹ️ 자동 복구됨 — 무슨 DDL이었는지 첨부 | 1시간 억제 |
| 에러 증가 + 위 조건 불충족 | 🚨 복구 안 됨 — worker·지연·워치독 마지막 판정 첨부 | 1시간 억제 |
| 자동 추종 대상이 아닌 타입 불일치 기록 중 | ⚠️ 시한폭탄 | 하루 1회 |

긴급 알림 문구도 바꿨다. 예전엔 "스킵되면 유실"이라고만 써서 오히려 SKIP을 떠올리게 했다.
지금은 "트랜잭션을 SKIP 하지 마세요 — 원인(주로 원본 DDL)을 맞추면 자동 재시도로 복구됩니다"라고
하지 말아야 할 행동부터 적는다. 워치독 조회가 실패하면 예전처럼 전부 긴급으로 보내도록 두었다.

## 배운 것

- **알림 등급은 사건이 아니라 현재 상태로 정한다.** "에러가 늘었다"만 보면 나은 장애와 진행 중인 장애가 같은 문구가 된다. 그러면 사람은 곧 둘 다 무시한다.
- **기록만 되는 경고는 없는 경고다.** 28번 기록된 경고는 0번 통보된 경고였다. 한 달 전 "7,768번 기록되고 0번 통보된 장애"와 같은 모양의 구멍이 다른 자리에 또 있었다.
- **자가치유를 설계할 땐 자동 범위 밖이 사람에게 도달하는 경로를 같이 만든다.** 자동으로 고치지 않기로 한 것은, 고칠 사람이 반드시 알아야 하는 것이다.
- **긴급 알림엔 해서는 안 될 행동을 먼저 적는다.** 급할수록 사람은 가장 빨라 보이는 버튼을 누른다. 여기서 그 버튼은 데이터를 영구히 버린다.
