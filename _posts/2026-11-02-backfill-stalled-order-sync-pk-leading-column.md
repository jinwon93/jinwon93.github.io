토요일 오후 3시, "주문 동기화 정체" 알림이 왔다. 통계 DB에 들어온 마지막 주문이 15:05에서 멈춰 있었다.
원본 주문 DB에서 5분마다 새 주문을 가져와 UPSERT 하는데, 그 UPSERT가 2.9초 → 5초 → 8초로 늘다가
API 역할의 statement_timeout(8초)을 넘기 시작했다. 한 번 실패하면 다음 배치가 더 커지고, 더 커진 배치는 또 실패했다.
알림은 "레플리카 구독 상태를 점검하라"고 안내했지만 레플리카는 멀쩡했다.

## 추적 — 범인은 내가 전날 건 백필이었다

대기 이벤트는 전부 `DataFileRead`였다. 디스크를 누가 붙잡고 있었는데, 전날 오후에 등록한 백필 cron이었다.
태그 체계를 크게 바꾼 뒤 과거 942일치 코드별 집계를 다시 계산하려고 1분마다 돌게 해 둔 작업이다.

| 지표 (24시간) | 값 |
|---|---|
| 백필 실행 / 실패 | 751회 / 630회 |
| 5분 실시간 집계 실패 | 288회 중 244회 |
| 새벽 정기 작업 | 10개가 2분 제한 초과로 실패 |

하루치 재계산이 2분을 넘으면 cron이 끊고, 같은 날짜를 1분 뒤 다시 시작한다. 끝나지 않는 일을 무한히 반복하며
디스크를 읽고 있었다. 백필을 끄자 다음 회차에 밀린 4만 3천 건이 12초 만에 들어갔다.

여기까지가 응급조치였고, 진짜 질문은 **평소 6초라던 하루치 재계산이 왜 100초씩 걸렸나**였다.
함수를 단계별로 쪼개 `EXPLAIN (ANALYZE, BUFFERS)`로 재 봤다.

| 단계 | 시간 | 읽은 블록 |
|---|---|---|
| 그날 집계할 행 고르기 | 1.2s | 1.5천 |
| 사라진 태그 행 정리(DELETE) | **97.8s** | **13.8만 (약 1GB)** |
| 코드 합계 다시 만들기 | **24.7s** | 7.7만 |

집계 테이블의 PK는 `(매장, 날짜, 메뉴, 코드)`였다. 정리 쿼리는 `WHERE 날짜 = $1` 만 걸었다.
PK의 **선두 컬럼이 매장이라 날짜 조건만으로는 범위를 좁힐 수 없고**, 플래너는 1GB짜리 PK를 처음부터 끝까지 훑었다.
날짜 BRIN 인덱스도 있었지만, 백필이 행을 다시 쓰면서 한 날짜의 행이 파일 전체로 흩어져 lossy 블록만 3.8만 개를 돌려줬다.
"평소 6초"는 최근 날짜가 캐시에 올라와 있을 때 숫자였다.

## 해결 — 매장 목록을 먼저 뽑는다

매장은 수백 곳뿐이다. PK 선두 컬럼의 고유값을 재귀 CTE로 건너뛰며 뽑으면(loose index scan) 수 밀리초면 된다.
그 배열을 조건에 붙이면 PK 앞 두 컬럼으로 바로 찾아간다. 조건이 항상 참이라 결과는 같다.

```sql
with recursive s as (
  (select sto from daily_code_stats order by sto limit 1)
  union all
  select (select a.sto from daily_code_stats a where a.sto > s.sto order by a.sto limit 1)
    from s where s.sto is not null
)
select array_agg(sto) into v_stos from s where sto is not null;

delete from daily_code_stats
 where sto = any(v_stos) and stat_date = p_date and ...;
```

| 단계 | 전 | 후 |
|---|---|---|
| 정리 DELETE | 97.8s | 6.4s |
| 코드 합계 | 24.7s | 0.94s |
| 하루치 전체 | 60~120s | **1.3~2.7s** |

독립 SQL로 다시 계산한 값과 행 단위로 `EXCEPT` 해서 0/0을 확인했다. 백필은 5분 간격, 영업·새벽 배치를 피한 시간대로 다시 켰다.

## 같은 병, 그리고 고쳤더니 더 느려진 것

주문 원본 테이블도 PK 선두가 매장이었고, 주문 한 건은 결제·상태 변경으로 평균 2.6번 다시 저장된다.
HOT 갱신이 28%뿐이라 나머지는 아무 빈 페이지로 옮겨 가, 하루치를 찾는 BRIN이 6만 블록을 돌려줬다.
같은 처방으로 주문방식 집계는 36초 → 4.7초, 요일·시간대 메뉴 집계는 23.5초 → 1.3초가 됐다.
후자는 원인이 하나 더 있었다. 날짜 컬럼은 `char(8)`인데 변수를 `text`로 선언해 컬럼 쪽이 캐스팅됐고,
인덱스를 아예 못 타서 하루치마다 3GB 품목 테이블을 전부 읽고 있었다. 테이블에는 `fillfactor = 85`도 걸었다.

그런데 같은 방식을 **여러 날을 읽는 점검 함수 4개**에 적용하자 오히려 느려졌다. 4일치에 20.8초, 원래 Seq Scan은 6~10초였다.
읽는 블록은 줄었지만 흩어진 힙을 무작위로 읽었고, 이 인스턴스에서는 무작위 읽기가 순차 읽기보다 블록당 수십 배 느렸다.
넷 다 원래 함수로 되돌렸다.

## 재발 방지

- **반복 실패 감시** — 연속 2회 또는 최근 10회 중 8회 실패하면 슬랙에 알린다. 이름에 backfill이 들어간 임시 작업은 스스로 멈춘다.
  상시 작업은 멈추면 더 큰 사고라 알림만 보낸다. 첫 버전은 사흘 전 실패 기록만 보고 막 다시 켠 백필을 멈춰 버렸다.
  "마지막 실패가 최근일 것"이라는 조건을 빠뜨렸던 것이라, 조건을 더해 다시 배포했다.
- **정체 알림 세분화** — 같은 30분에 실행 6회 · 오류 6회 · 0건이면 "원본 정체"가 아니라 "DB 저장 실패"로 알리고 마지막 오류를 붙인다.
- 같은 날 아침 RLS 감시가 이 작업 중 만든 백업 테이블 6개가 공개 키에 열려 있다고 알렸다.
  9월에 붙인 그 감시다. 이번엔 노출 스키마 밖으로 옮겼다.

## 배운 것

- **PK 선두가 아닌 컬럼만으로 거는 조건은 인덱스 전체 스캔이다.** 선두 컬럼의 고유값이 적으면 먼저 뽑아 `= any()`로 붙이는 게 가장 싸다.
- **"평소 N초"는 캐시가 따뜻할 때 숫자다.** 과거 데이터를 다시 도는 작업은 차가운 캐시 기준으로 재야 한다.
- **블록 수를 줄이는 게 항상 빠른 건 아니다.** 단일 날짜는 인덱스, 여러 날 범위는 순차 스캔이 이겼다. 바꾼 뒤에도 다시 쟀다.
- **끝나지 않는 작업을 1분마다 재시도하게 두면 그 자체가 부하 공격이다.** 실패를 세고, 스스로 멈추게 해야 한다.
