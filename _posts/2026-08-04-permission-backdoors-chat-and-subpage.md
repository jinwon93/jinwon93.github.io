"장애접수 담당자가 AI 챗에서 매출을 물어보면 안 되잖아?" 팀에서 나온 질문이다.
확인해 보니 그쪽은 막혀 있었다 — 담당자 역할에는 판매 분석 도구가 아예
전달되지 않는다. 그런데 확인하는 김에 반대 방향을 열어봤더니, 거기가 뚫려
있었다. **장애접수 화면을 못 여는 사람이 챗으로는 티켓을 전부 조회할 수 있었다.**

## 추적: 같은 데이터로 가는 입구를 세어본다

권한 사고는 대개 판정 로직이 틀려서가 아니라, **판정을 안 거치는 입구가 하나
더 있어서** 난다. 그래서 티켓 데이터에 도달하는 경로를 전부 나열했다.

| 입구 | 게이트 |
|---|---|
| 목록 화면 / API | 페이지 권한 검사 ✅ |
| 통계 화면 / API | 페이지 권한 검사 ✅ |
| 하위 도구 화면(병합·옵션) | 자기 자신만 검사 ⚠️ |
| AI 분석 챗 | **없음** ❌ |

챗 라우트의 도구 배열은 이렇게 생겼다.

```ts
const tools = isEngineer ? CS_TOOLS : [...ANALYTICS_TOOLS, ...CS_TOOLS];
//                                                          ^^^^^^^^ 무조건
```

담당자 역할이 아니면 CS 도구가 **무조건** 붙는다. 화면에서는 페이지 권한으로
막아둔 데이터가, 챗에서는 자연어 한 줄로 나왔다.

더 나쁜 건 스코프였다. 판매 도구는 전부 "접근 가능 매장 목록"을 인자로
강제 주입한다 — 코드에서 세어보니 15군데. CS 도구 쪽에서 같은 목록을 참조하는
곳은 **0군데**였다. 조회 함수 자체에 매장 범위 파라미터가 없었고, 서비스 계정으로
호출하니 행 수준 보안도 우회됐다. 자기 매장 3개만 보게 되어 있는 계정이 전 매장
티켓 전문을 볼 수 있는 상태였다.

## 구멍 1: 도구 "목록"도 권한 면이다

예전 글에서 "권한은 LLM이 아니라 디스패처가 지킨다"고 썼다. 맞는 말인데
반쪽이었다. 그때 지킨 건 도구의 **인자**(매장 목록 주입)였고, 도구의
**목록** 자체는 아무도 안 지키고 있었다.

고친 방식은 새 게이트를 발명하지 않는 것이었다. 앱에는 이미 페이지 권한 판정
함수가 있다. 챗이 그걸 그대로 쓰게 만들고, 판매축과 CS축을 독립된 두 스위치로
분리했다.

```ts
const [canUseCs, accessible] = await Promise.all([
  canAccessPage(userId, role, "ops.cs"),          // 화면과 완전히 동일한 규칙
  salesRole ? getAccessibleStores(userId, role)
            : Promise.resolve([]),                 // fail-closed
]);
const canUseSales = salesRole && (accessible === null || accessible.length > 0);

const tools = [
  ...(canUseSales ? ANALYTICS_TOOLS : []),
  ...(canUseCs    ? CS_TOOLS        : []),
];
```

두 판정은 병렬이라 추가 지연이 없다. 판매 권한이 없으면 매장 목록을
`null`(전체 허용)이 아니라 `[]`(전면 차단)로 못박았다 — 나중에 도구 등록을
잘못 건드려도 "허용"이 아니라 "거부"로 실패하게.

부수 효과가 하나 있다. 시스템 프롬프트가 권한 조합(최대 4가지)마다 갈리므로
프롬프트 캐시 엔트리도 그만큼 늘어난다. 캐시 적중률과 권한 정합성을 맞바꾼
셈인데, 이 교환은 고민할 거리가 아니었다.

## 구멍 2: 하위 페이지에 부모가 없었다

권한 데이터를 훑다가 두 번째가 나왔다. "데이터 병합", "옵션 관리" 같은 하위
도구 화면에 개인 예외(override)가 걸린 계정이 있는데, **정작 부모인 목록
화면 권한은 없었다.**

판정 함수는 요청된 페이지 키 하나만 본다. 그래서 이 계정들은 목록 화면은
못 열지만 하위 도구 URL은 직접 입력으로 열렸다. 병합 화면은 원본 데이터가
그대로 노출되고, 옵션 관리는 분류 체계를 **쓰기**하는 화면이다.

2축 모델(역할 기본 × 개인 예외)에 계층 축이 없었던 것이다. 부모 ∧ 자식으로
바꿨다.

```ts
export async function canAccessSubPage(userId, role, pageKey) {
  if (pageKey === ROOT_PAGE) return canAccessPage(userId, role, ROOT_PAGE);
  const [parent, child] = await Promise.all([
    canAccessPage(userId, role, ROOT_PAGE),
    canAccessPage(userId, role, pageKey),
  ]);
  return parent && child;
}
```

공용 인증자가 이 함수를 쓰게 하니 API 21개 지점이 한 번에 커버됐다. 화면(SSR)
가드와 사이드바 메뉴에도 같은 규칙을 심었다. 메뉴 숨김은 보안이 아니지만,
**서버가 막는 것과 화면이 보여주는 것이 어긋나 있으면 그 자체가 다음 사고의
씨앗**이라 셋을 같은 규칙으로 맞췄다. 죽은 예외 3행은 삭제했다 — 권한 관리
화면에 "부여됨"으로 남아 있으면 다음 사람이 반드시 오해한다.

## 결과

| 항목 | 전 | 후 |
|---|---|---|
| 챗에서 CS 도구를 받는 역할 | 담당자 제외 전 역할 | 페이지 권한 보유자만 |
| CS 도구의 매장 스코프 | 참조 0군데 | 권한 미보유 시 도구 자체 미전달 |
| 하위 도구 URL 직접 진입 | 가능 | 부모 ∧ 자식으로 차단 |
| 판정 규칙 소스 | 화면·API·챗 제각각 | 단일 함수 |

권한이 줄어든 실사용자는 0명이었다. 없어진 건 정확히 우회 경로뿐이다.

## 배운 것

- 권한 감사는 "판정이 맞나"가 아니라 **"같은 데이터에 이르는 입구를 전부
  세었나"**로 시작해야 한다. 구멍은 대개 가장 늦게 만든 입구에 있다.
- LLM 시스템에서 권한 경계는 도구 실행 계층만이 아니다. **어떤 도구를 건네느냐**
  자체가 권한 면이다. 인자를 아무리 잘 필터해도 목록이 새면 소용없다.
- 새 게이트를 발명하지 말고 **앱이 이미 가진 단일 진실 소스를 재사용**하라.
  규칙이 두 벌이 되는 순간 둘은 반드시 어긋난다.
- 계층이 있는 리소스에 평면 권한 모델을 쓰면 자식만 열린 상태가 만들어진다.
  부모 없는 자식 권한은 **데이터가 아니라 모델의 버그**다.
