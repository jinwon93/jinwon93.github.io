E2E 테스트를 새로 붙이고 처음 돌린 날, "최근 6회 증분 수집이 모두 0건" 케이스가 빨간불로 떴다.
확인해보니 전날 오후 1시 15분을 마지막으로 주문 데이터가 23시간째 들어오지 않고 있었다.
하루 4만 건이 들어오던 파이프라인이 6,051건에서 멈춰 있었고, 그날치는 0건이었다.

한 달 전 같은 장애를 두 번 겪고 워치독을 붙여둔 상태였다. 그 워치독은 이번에도 정상 작동했다.
10분마다 `slot_lost`를 기록했고, 30분마다 적용 에러 증가분을 스냅샷에 남겼다.
문제는 그 기록이 아무에게도 도달하지 않았다는 것이다.

## 추적

레플리카의 워치독 로그부터 봤다. 판정은 명확했다.

```
action=slot_lost / wal_status=lost / worker_pid=null / apply_errors=7768
"슬롯 무효화 — 수동 재생성 + 공백 구간 백필 필요"
```

에러 카운터의 증가 패턴이 특이했다. 30분마다 정확히 360건씩, 즉 5초에 한 번씩 규칙적으로 올랐다.
적용 워커가 특정 트랜잭션에서 죽고 재시작하기를 반복하는 크래시 루프였다.
복제가 멈춘 동안 미전송 WAL이 쌓였고, 보존 상한 4GB를 넘자 Postgres가 슬롯을 폐기했다.
축적 속도가 시간당 약 82MB였으니 **장애 발생 후 6시간이 한계선**이었다는 계산이 나온다.

여기까지는 감시가 다 잡아낸 내용이다. 그런데 알림 상태 테이블을 열어보니 비어 있었다.

```sql
SELECT count(*) FROM reporting.alert_state;  -- 0
```

알림 발송 함수는 시크릿 저장소에서 웹훅 URL을 조회한 뒤, 없으면 경고 로그만 남기고
`false`를 반환하도록 되어 있었다. 그 URL이 한 번도 등록된 적이 없었다.
감시 함수 다섯 개가 10~30분 주기로 성실히 돌면서, 전부 조용히 `false`를 받고 끝나고 있었다.

## 해결

슬롯 재생성은 정석대로 진행했다. 구독 분리 → 원본에서 죽은 슬롯 제거·재생성 → 재연결.
2분 만에 복제가 재개됐다. 문제는 그다음이었다.

슬롯을 새로 만들면 **재생성 시점 이후의 WAL만** 받는다. 끊긴 23시간 구간은 자동으로 메워지지 않는다.
그 구간을 FDW로 원본에서 직접 복사했는데, 복사를 먼저 하고 복제를 붙였더니 PK 충돌이 터졌다.

```
duplicate key value violates unique constraint "..._pkey"
→ apply worker exited with exit code 1  (5초마다 반복)
```

내가 채워 넣은 행과 복제가 보내려는 행이 겹친 것이다. 순서를 뒤집어 해결했다.
해당 구간을 비우고 **복제를 먼저 안정화시킨 뒤, 남은 공백만 채웠다.**

또 하나 걸린 것은 PK와 UNIQUE 제약이 다른 테이블이었다.
PK는 `id`인데 UNIQUE는 `(shop_cd, table_cd)`였고, 원본에서 전량 삭제 후 재삽입되는 패턴이었다.
복제가 끊긴 동안 DELETE가 유실되니 옛 행이 남았고, 새 행이 들어오려다 UNIQUE에 걸렸다.
전체 14,180행 중 **10,698행(76%)이 원본에 없는 유령 행**이었다.
이런 테이블은 복제가 한 번만 끊겨도 반드시 충돌한다.

## 결과

| 항목 | 장애 시 | 복구 후 |
|---|---|---|
| 복제 워커 | 미가동 (5초 주기 크래시) | 가동, 랙 0초 |
| WAL 랙 | 909MB (증가 중) | 162KB |
| 적용 에러 | 7,768 (증가 중) | 7,768 **고정** |
| 유실 행 | 약 17만 행 | 0 (FDW 백필) |
| 미감지 시간 | **23시간** | 알림 연동 완료 |

웹훅을 등록하자 감시 다섯 개가 한꺼번에 살아났다. 등록 직후 실제 경보가 한 번 발화했는데,
크래시 루프 마지막 순간의 증가분을 뒤늦게 비교한 것이었다. 오탐이었지만
**감시 → 판정 → 발화 → 전달** 전 경로가 살아있다는 확인이 됐다.

## 배운 것

- **감시를 만드는 것과 알림이 도달하는 것은 별개의 일이다.** 감시 코드는 다섯 개가 완비돼 있었고
  전부 정상 동작했다. 비어 있던 건 마지막 1미터, 시크릿 저장소의 URL 한 줄이었다.
  감시를 붙였으면 반드시 테스트 발송으로 끝단까지 확인해야 한다.
- **알림 실패를 조용히 넘기면 안 된다.** 웹훅이 없을 때 `false`를 반환하고 끝내는 설계 탓에,
  알림이 안 가고 있다는 사실 자체가 은폐됐다. 전달 실패는 그 자체로 경보 대상이어야 한다.
- **복제 복구는 순서가 지배한다.** 슬롯 재생성 후에는 복제를 먼저 안정화시키고 공백을 나중에 채워야 한다.
  반대로 하면 겹치는 구간에서 PK 충돌로 또 다른 크래시 루프가 생긴다.
- **PK와 UNIQUE가 다른 테이블은 논리복제의 시한폭탄이다.** 복제는 PK로 행을 식별하므로,
  전량 교체 패턴 + 제약 불일치 조합은 복제가 끊길 때마다 충돌을 만든다.
- 보존 상한이 곧 대응 시간이다. WAL 4GB는 이 트래픽에서 6시간이었다. 새벽이나 주말에
  터지면 손쓸 시간이 없다는 뜻이라, 상한 자체를 늘리는 것도 감시만큼 중요하다.
