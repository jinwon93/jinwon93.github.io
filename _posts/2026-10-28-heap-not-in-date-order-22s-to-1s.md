통계 대시보드에서 "최근 30일 · 전체 매장"을 처음 열면 메뉴 랭킹이 16초, 코드 분석이 7~12초 걸렸다.
라우트에 결과 캐시를 붙여 같은 조건 재조회는 0.25초가 됐지만, 첫 조회는 그대로였다.
조회 RPC 전부를 같은 조건으로 `EXPLAIN (ANALYZE, BUFFERS)` 해 보니 1초를 넘는 것이 10개, 가장 느린 것은 22.3초였다.

## 원인 — 30일치가 파일 전체에 흩어져 있었다

느린 조회들에 공통점이 하나 있었다. **팩트 테이블의 물리 순서가 날짜순이 아니었다.**

- 일별 메뉴 집계(3.6GB)는 매장별 동기화가 매장 단위로 덮어써서, 30일치 30만 행이 파일 곳곳에 흩어져 있었다.
  매장 배열로 훑으면 10만 버퍼 이상을 무작위로 읽었다.
- 매장·코드별 일 집계는 날짜 컬럼의 상관도가 −0.007, 사실상 무작위였다. BRIN이 있어도 걸러 낼 범위가 없다.
- 시간대 집계는 PK가 `(매장, …)`라 매장 472곳을 하나씩 찔러 9.6만 버퍼를 만졌다.

함수는 31일을 넘으면 월 단위 MV를 쓰도록 되어 있었다. 그래서 하필 "30일" 프리셋이 원본 일 집계를 끝까지 읽는 최악 구간이었다.

## 해결 — 날짜순 슬림 사본 + 오늘은 원본

조치는 하나로 통일했다. 야간 배치가 **화면에 필요한 컬럼만, 테스트 매장을 빼고, 날짜순으로** 담은 슬림 사본을 만든다.
조회는 사본 + 오늘 원본을 합친다.

```sql
-- 사본의 마지막 날짜 다음부터는 원본에서 읽는다 (보통 오늘 하루, ≈0.1s)
v_live_from := least(
  (select max(stat_date) + 1 from menu_rollup_daily),
  (now() at time zone 'Asia/Seoul')::date);
```

배치가 며칠 멈춰도 원본을 더 읽을 뿐 숫자가 틀리지는 않는다. 오늘 데이터를 5분마다 다시 굽는 방식은
하루 1,100만 개의 dead tuple을 만들어서 택하지 않았다.

함정이 하나 있었다. 사본을 만들어 놓고도 첫 측정에서 30일 PK 스캔이 **25만 버퍼**를 만졌다. 적재 순서가 PK와 달라
하루 안에서 힙을 오갔던 것이다. `INSERT … SELECT … ORDER BY <PK>`로 다시 적재하자 **5.7천 버퍼**가 됐다.
사본이라도 순서는 넣을 때 정해 줘야 한다.

| 조회 | 전 | 후 |
|---|---|---|
| 매출 변동 요인 — 메뉴 축 | 22,258 ms | **998 ms** |
| 주간 리포트 | 21,858 ms | **452 ms** |
| 지역 메뉴 가격 (30일) | 18,249 ms | **733 ms** |
| 코드별 메뉴 랭킹 | 12,317 ms | **737 ms** |
| 메뉴 랭킹 | 9,903 ms | **710 ms** |
| 코드 분석 | 7,798 ms | **33 ms** |

정합성은 3~10월을 월 단위로 잘라, 기존 매장별 경로와 TOP20·TOP100의 순위와 값을 하나씩 대조해 일치를 확인했다.

## 덤으로 잡힌 것 두 개

**제네릭 플랜 고착.** 피크타임 조회는 처음 다섯 번은 빠르다가 여섯 번째부터 690ms로 굳었다.
PL/pgSQL의 준비된 문장이 다섯 번 뒤 제네릭 플랜으로 바뀌면서, 기간·매장 수와 상관없는 평균 계획에 고정된 것이다.
`EXECUTE … USING`으로 매번 커스텀 플랜을 받게 바꾸자 113~127ms로 안정됐다.

**월 경계 과대.** 32일 이상 기간에서는 월 MV를 쓰는데, 시작일이 속한 달의 **1일부터** 합산하고 있었다.
90일 메뉴 랭킹이 약 30% 부풀어 있었다. 기간에 걸친 행만 돌려주는 공용 함수를 하나 두고 코드 분석·피크타임·메뉴 함수가 모두 그것을 쓰게 했다.
31일 이하 대조군과 365일 혼합 구간까지 일 단위 정답과 `EXCEPT` 0/0을 확인했다.

## 배운 것

- **느린 조회의 원인이 쿼리가 아니라 저장 순서일 때가 있다.** 버퍼 수가 결과 행 수에 비해 터무니없이 크면 힙 순서부터 의심한다.
- **사본·롤업도 적재 순서를 지정해야 한다.** `ORDER BY` 하나로 버퍼가 25만에서 5.7천이 됐다.
- **"오늘은 원본"으로 경계를 두면 배치 지연이 오류가 아니라 비용이 된다.** 틀리는 것보다 조금 느린 게 낫다.
- **빨라졌다면 정답과 다시 맞춘다.** 이번에 성능을 보다가 30% 과대라는 기존 정합성 버그를 같이 찾았다.
