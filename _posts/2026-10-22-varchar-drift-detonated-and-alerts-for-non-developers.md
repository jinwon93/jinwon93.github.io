[9월 말 글](/2026/09/auto-recovered-alarm-and-silent-type-drift/)에서
"원본은 varchar를 늘렸는데 레플리카는 그대로"인 상태를 시한폭탄이라 부르고, 하루 한 번 경고를 보내도록 만들었다.
오늘 오전 11시 30분, 같은 모양의 경고가 다른 테이블 4개에서 떴다. 이번엔 10분 만에 실제로 터졌다.
레플리카 적용이 멈췄고, 밀린 변경분이 50분 동안 390MB까지 불었다.

## 추적

워치독 기록을 시간순으로 놓으면 사건이 그대로 보인다.

| 시각 | 판정 | 랙 | 누적 적용 에러 |
|---|---|---|---|
| 11:20 | ok | 56B | 12,093 |
| 11:30 | schema_drift — 분류 코드 컬럼 6개 `pub=varchar(10) rep=varchar(4·6)` | 12MB | 12,093 |
| 11:40 | apply_error (+71) | 49MB | 12,164 |
| 12:00 | apply_error (+120) | 216MB | 12,404 |
| 12:20 | apply_error (+120) | 390MB | 12,644 |

원본에서 분류 코드 테이블 4개의 코드 컬럼을 4~6자에서 10자로 늘렸다. 논리복제는 DDL을 옮기지 않는다.
10분 뒤 7자 이상 코드가 처음 들어오자 레플리카 적용이 `value too long`으로 넘어졌고,
worker는 5초마다 같은 트랜잭션을 재시도하다 다시 죽었다. 10분에 120번, 정확히 5초 간격이다.

그런데 11:40부터 나간 긴급 알림에는 원인이 이렇게 적혀 있었다.

```
스키마 드리프트 아님(컬럼·타입·NOT NULL 점검 통과). 제약 충돌 추정(UNIQUE/FK/CHECK).
```

바로 10분 전 같은 워치독이 "타입 불일치"라고 기록해 놓고, 에러 원인을 짚을 때는 "타입 점검 통과"라고 했다.
에러 진단 단계가 타입 **이름**(`character varying`)만 비교하고 **길이**는 보지 않았기 때문이다.
알림만 믿고 움직였다면 있지도 않은 중복 키를 찾아 로그를 뒤지고 있었을 것이다.

## 해결

원인이 길이라면 해법은 9월과 같다. 레플리카 컬럼을 원본 길이로 늘린다.
varchar 확장은 테이블을 다시 쓰지 않으므로 즉시 끝나고 조회도 막지 않는다.

```sql
alter table 스키마.분류테이블 alter column 코드컬럼 type varchar(10);  -- 4개 테이블 · 6개 컬럼
```

적용 직후 worker가 막혀 있던 트랜잭션을 재시도로 적용했다. SKIP이 아니라 재적용이니 유실은 없다.

| 구분 | 12:20 (조치 전) | 12:30 (조치 후) |
|---|---|---|
| 랙 | 390MB | 0.4MB |
| 10분간 에러 증가 | +120 | 멈춤 (12,690 고정) |
| worker | 크래시 루프 | 가동, 마지막 수신 0.03초 전 |

## 그다음 문제: 내가 자리에 없으면

복구하고 나니 더 큰 질문이 남았다. 이 알림을 받는 슬랙 채널의 대부분은 개발자가 아니다.
"apply_error_count", "UNIQUE/FK/CHECK"는 그들에게 아무 뜻도 없다. 반대로 매장 정보 누락이나
통계 집계 누락처럼 시스템 상태 화면의 버튼 하나로 끝나는 장애도, 알림 문구만으로는 그걸 알 방법이 없었다.

그래서 알림 본문을 같은 4단 틀로 다시 썼다.

```
📍 무슨 일인가요?          — 화면에서 어떻게 보이는지, 주문·결제에 영향이 있는지
✅ 이렇게 해 주세요         — 시스템 상태 → 운영 → [매장만] 같은 버튼 경로 (버튼으로 되는 경우만)
🙋 개발자에게 넘길 때       — "버튼을 눌러도 다음 알림에 또 나오면"처럼 판단 기준
🔧 개발자용 상세            — 기존 기술 문구는 맨 아래로
```

핵심은 **버튼으로 되는 것과 안 되는 것을 알림이 대신 판정하는 것**이다. 통계 대조 알림은 날짜마다
방향을 갈라, 통계가 원본보다 적은 날(집계 누락)에만 "통계 집계 → 날짜 → 집계 실행"을 안내하고,
원본이 더 적은 날(적재 유실)은 "버튼으로 해결되지 않아요 — 개발 담당자에게"로 보낸다.
신규 매장 정보가 아직 안 넘어온 경우는 지금까지 슬랙을 아예 보내지 않았는데, 버튼 한 번이면 끝나는 일이라
안내와 함께 보내도록 바꿨다. 감지 기준과 알림 주기는 하나도 건드리지 않았다.

다음 단계는 오늘 같은 일에 사람이 아예 필요 없게 하는 것이다. 워치독은 이미 컬럼 추가와 NOT NULL 차이를
스스로 맞춘다. "같은 타입이고 원본이 더 길다"는 늘리기만 하면 되는 안전한 방향이라 같은 급으로 자동 처리할 수 있다.
줄이거나 타입 자체를 바꾸는 경우는 여전히 사람에게 넘긴다.

## 배운 것

- **같은 사실을 두 단계가 다르게 보면, 늦게 도는 단계의 판정이 알림에 실린다.** 드리프트 감지는 길이를 봤고 에러 진단은 안 봤다. 진단 로직은 감지 로직과 같은 비교 함수를 써야 한다.
- **"시한폭탄" 경고에는 터졌을 때의 모습도 같이 적어 둔다.** 3주 전 경고가 "넘는 순간 무한 크래시"라고 적어 둔 덕에, 잘못된 진단 문구를 보고도 원인을 바로 연결했다.
- **알림은 받는 사람이 할 수 있는 행동으로 끝나야 한다.** 비개발자에게 "제약 충돌 추정"은 행동이 아니다. "운영 → 매장만" 또는 "개발 담당자에게 전달"은 행동이다.
- **사람에게 맡길지 자동으로 고칠지는 '되돌릴 수 있는가'로 나눈다.** 늘리기는 안전하니 자동, 줄이기와 타입 변경은 데이터가 걸려 있으니 사람.
