사내 운영 포털을 두 달 붙들고 기능을 붙이다 보니, 어느 화면은 "누르면 좀 기다려야 한다"는
말이 나오기 시작했다. 그런데 느린 쿼리를 찾아보면 없었다. 실행계획은 다 깨끗했고
대시보드 집계도 밀리초 단위였다. 그래서 기능 추가를 멈추고 전수 조사를 했다.
결론은 **쿼리 비용이 아니라 왕복 횟수**였고, 인덱스는 한 개도 추가하지 않았다.

## 추적: 테이블 통계가 먼저 말했다

느린 쿼리 목록보다 먼저 본 건 테이블 접근 통계다. 어떤 테이블이 학대당하고 있는지는
여기가 가장 빨리 알려준다.

```sql
select relname, n_live_tup, seq_scan, seq_tup_read, idx_scan
from pg_stat_user_tables
order by seq_tup_read desc
limit 10;
```

상위에서 눈이 멈춘 줄은 이랬다. **사용자 테이블: 살아있는 행 15개, 순차 스캔 330,918회,
읽은 튜플 394만, 인덱스 스캔은 세 자릿수.**

15행짜리 테이블에 플래너가 순차 스캔을 고르는 건 정상이다. 인덱스를 타는 쪽이 더 비싸다.
문제는 그게 아니라 **33만 번**이라는 숫자였다. 15행 × 33만 회 = 394만 튜플. 한 번당
비용이 0에 가까워도 33만 번이면 총량이 생긴다. 이건 튜닝할 쿼리가 아니라, **호출부를
봐야 한다는 신호**다.

`pg_stat_statements`도 같은 방향을 가리켰다. 앱 경로 중 가장 무거운 것이 평균 205.8ms에
호출 105회. 총 실행시간 기준으로는 존재감이 없었다. 즉, 비싼 쿼리는 없었다.

## 원인: API 한 번에 인증 왕복 3회

호출부를 따라가니 답이 단순했다. 서버 라우트마다 앞단에서 이걸 한다.

1. 세션 → 사용자 레코드 조회
2. 역할(role) 검증
3. 해당 페이지 접근 권한 조회 (개인 오버라이드 → 역할 권한, **순차로** 두 번)

즉 API 하나당 DB 왕복 3회, 그중 2회가 15행 테이블 조회다. 화면 하나를 그릴 때 API를
4~5개 부르니 **렌더 한 번에 12~15회**가 쌓인다. 왕복 하나가 10~20ms라도 합치면 체감
지연이 되고, 통계에는 33만 번의 순차 스캔으로 남는다.

## 해결: 캐시 30초, 그리고 순차를 병렬로

같은 요청 처리 중에 권한이 바뀔 확률은 사실상 0이다. 그래서 30초 TTL 인메모리 캐시를
붙였다. 다만 **성공만 캐싱**했다.

```ts
// 실패·부재는 캐싱하지 않는다 —
// 방금 승인된 계정이 30초를 기다릴 이유가 없다
const hit = readAuthCache(metaUserCache, key);
if (hit) return hit;
const user = await fetchMetaUser(key);
if (user) writeAuthCache(metaUserCache, key, user);
```

여기에 세 가지를 더했다. 권한 변경 API에서 캐시를 **명시적으로 무효화**해 관리자가
방금 바꾼 권한이 30초간 안 먹는 상황을 막았고, 순차로 돌던 오버라이드·역할 권한 조회를
병렬로 합쳤고, 외부 복제 DB를 읽는 부가 정보 조회에는 `statement_timeout`을 걸었다.
화면 한 구석의 보조 정보 때문에 페이지 전체가 끌려가면 안 된다.

나머지는 payload 다이어트였다. 목록 메타 API가 매장 3,000행을 항상 실어 보내던 것을
필요한 화면만 받게 나눴고, O(n²) 유사도 클러스터링 결과에 10분 캐시를 붙였고,
1,000행을 한 번에 그리던 이력 영역은 50행 단위로 끊었다.

## 덤: "완료"의 정의가 다섯 군데 있었다

성능을 보러 들어갔다가 더 나쁜 걸 발견했다. 티켓 상태 중 "완료로 간주하는 집합"이
코드와 DB에 **서로 다르게 다섯 번** 하드코딩돼 있었다. 상태 옵션 배열, 목록 필터,
KPI 집계 함수, 완료 시각 스탬프 조건, 배지 스타일. 그래서 새 완료 상태를 하나 추가한
뒤로, 그 상태로 접수하면 **완료 시각이 기록되지 않았고**(따라서 처리 시간 통계에서
사라졌고) 지식화 후보 추출에서도 빠졌다. 아무 에러도 나지 않아서 아무도 몰랐다.

앱 쪽은 상수 파일 하나와 `isClosedStatus()` 로 모았다. DB 함수 4개는 손으로 다시 쓰지
않고 정의를 읽어 치환하는 방식으로 처리했다 — 멱등하고, 다시 돌려도 안전하다.

```sql
select pg_get_functiondef(p.oid) into def
  from pg_proc p join pg_namespace n on n.oid = p.pronamespace
 where n.nspname = 'app' and p.proname = fn and p.prokind = 'f';
def := replace(def, '(''처리완료'',''자체해결'')',
                    '(''처리완료'',''자체해결'',''방문처리완료'')');
execute def;
```

같은 조사에서 참조 없는 파일 21개(백업 `.bak`, 번호 붙은 라우트 사본, 조각 `.txt`)도
정리했다. 외부 참조 0건을 확인한 뒤에만 옮겼다.

| 지표 | 전 | 후 |
|---|---|---|
| API 호출당 인증 왕복 | 3회 | 0~1회 (30초 캐시) |
| 화면 1회 렌더 왕복 | 12~15회 | 1~2회 |
| 권한 조회 | 순차 2회 | 병렬 1회 |
| 목록 메타 payload | 항상 3,000행 | 필요한 화면만 |
| "완료" 상태 정의 위치 | 5곳 | 1곳 |
| 추가한 인덱스 | — | 0개 |

## 배운 것

- `n_live_tup`이 두 자릿수인 테이블이 `seq_tup_read` 상위에 있으면 쿼리를 고칠 게 아니라
  **호출 횟수를 고쳐야 한다.** 테이블 통계는 코드 리뷰보다 정직하다.
- 캐시는 **성공만** 담는다. 실패와 부재를 캐싱하면 성능 개선이 권한 지연 버그로 바뀐다.
- "같은 개념이 몇 군데 정의돼 있는가"는 성능 항목이 아니라 **감사 항목**이다. 다섯 군데면
  언젠가 네 군데만 고치고, 조용히 통계가 틀린다.
- 함수 본문 일괄 수정은 `pg_get_functiondef` + `replace` + `execute` 가 손으로 다시 쓰는
  것보다 안전하다. 실수할 자리가 없다.
- 두 달 동안 기능을 붙였으면 하루는 조사에 쓰는 게 남는 장사다. 이번엔 성능 5건과
  통계 정확성 버그 1건이 같은 조사에서 나왔다.
