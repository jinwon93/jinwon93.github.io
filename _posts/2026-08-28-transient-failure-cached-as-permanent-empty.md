CS(장애접수) 통계에 '매장당 운영 부담 추이' 카드가 하나 있다.
일/주/월/년 단위를 카드 안에서 바꿔가며 보는 위젯인데, 어느 날부터 특정 단위에서
"해당 기간에 데이터가 없습니다"가 떴다. 그런데 같은 페이지 다른 카드엔 그 기간 데이터가 멀쩡히 있었고,
**새로고침하면 그 단위도 정상**이었다. 단위를 바꿨다가 돌아와도 여전히 "데이터 없음"인데, F5 한 번이면 나았다.

"데이터가 없는데 새로고침하면 생긴다"는 건 데이터 문제가 아니라 상태 문제다.

## 카드가 응답을 캐시하는 방식

이 카드는 단위마다 응답을 캐시한다. 일↔월을 오가며 비교하는 게 주 사용법이라
매번 다시 받으면 이미 본 화면을 또 기다리기 때문이다. 캐시 키는 `기간|단위`,
로딩은 상태로 두지 않고 캐시 적중 여부에서 파생시켰다.

```tsx
const [cache, setCache]   = useState<Record<string, LoadResp>>({});
const [failed, setFailed] = useState<Record<string, true>>({}); // 실패한 키 — 무한 로딩 방지용

const key     = `${range.from}|${range.to}|${grain}`;
const data    = cache[key] ?? null;
const loading = !data && !failed[key];

useEffect(() => {
  if (cache[key] || failed[key]) return;        // 캐시 적중·이미 실패 → 네트워크 안 탄다
  // ... fetch → 성공하면 setCache, 실패하면 setFailed(key)
}, [key, grain, range.from, range.to, cache, failed]);
```

`failed`는 원래 좋은 의도였다. 이게 없으면 요청이 실패했을 때 `loading`이
영영 `true`로 남아 "불러오는 중…"이 안 사라진다. 그래서 실패한 키를 기록해
로딩을 끝내려는 것이었다.

## 함정: 실패에는 수명이 없었다

문제는 `failed`에 **만료도 재시도 경로도 없다**는 것이었다.

`/api/stats/cs/load`가 한 번 500을 뱉거나 네트워크가 순간 끊기면 `setFailed(key)`가 찍힌다.
그 순간부터 effect의 첫 줄 `if (cache[key] || failed[key]) return`이 그 키의 **모든 재요청을 막는다.**
단위를 바꿨다 돌아와도 `failed[key]`가 그대로라 다시 요청하지 않고, `failed`는 어디서도 지워지지 않는다.
결국 **페이지를 새로 열기 전까지** 그 단위는 계속 "데이터 없음"이다.

한 번의 일시적 실패가 세션 전체에서 영구 상태가 된 것이다.

왜 예전엔 이런 일이 없었나 봤더니, 캐시를 붙이기 전 버전은 단위가 바뀌면 그냥 다시 받았다.
일시적으로 실패해도 다음에 그 단위로 돌아오면 재요청이 나가 **스스로 나았다.**
성능을 위해 캐시를 넣으면서, 그 자가 치유를 같이 없애버린 셈이다.
최적화가 회복 경로를 지운 전형적인 사례다.

## 더 깊은 문제: 세 상태를 둘로 접었다

빈 화면 렌더도 다시 보니 같은 뿌리였다.

```tsx
{loading ? (
  <div>불러오는 중...</div>
) : rows.length === 0 ? (
  <div>해당 기간에 데이터가 없습니다.</div>   // ← failed[key] 도 여기로 온다
) : ( /* 차트 */ )}
```

`failed[key]`가 참이면 `loading`은 `false`, `rows`는 비어 있으니
사용자는 "해당 기간에 데이터가 없습니다"를 본다. 서버가 죽었는데 화면은
**"이 기간엔 접수가 0건이었다"**고 말한다. 장애가 정상 상태로 위장된 것이다.

로딩·빈 데이터·에러는 **서로 다른 세 상태**다. 그런데 코드는 이걸 둘(로딩 / 나머지)로 접었고,
접히는 순간 "불러오지 못함"과 "불러왔더니 0건"이 구분되지 않았다.

## 해결

세 가지를 나눠 고쳤다.

**1. 실패를 캐시 가드에서 뺐다.** 가드는 성공 캐시만 본다. 그러면 단위를 바꿨다 돌아올 때
(키가 바뀌면) 다시 요청이 나가 예전처럼 스스로 낫는다. 같은 단위에서 즉시 재시도하려면
nonce 하나로 effect를 다시 트리거한다.

```tsx
useEffect(() => {
  if (cacheRef.current[key]) return;   // 성공 캐시만 재사용 — 실패는 여기서 안 막아 self-heal
  // ... fetch: 실패 → setErrored(key), 성공 → setCache + setErrored 해제
}, [key, grain, range.from, range.to, reloadNonce]);
```

**2. 에러 상태를 빈 상태와 분리했다.** `isError`면 "데이터를 불러오지 못했습니다 · 다시 시도" 버튼을
보여준다. 장애를 0건으로 오독하지 않는다.

**3. 로딩 중엔 이전 차트를 흐리게 유지했다(stale-while-revalidate).** 캐시 안 된 단위로
처음 전환할 때 화면이 빈 박스로 사라지던 걸, 마지막 성공 데이터를 `opacity-50`으로 깔고
그 위에 "불러오는 중"을 얹는 방식으로 바꿨다. 비교가 이 카드의 목적인데 전환마다 그림이
사라지면 그 목적이 깨진다.

여기에 한 가지 프레임워크 제약이 구현 형태를 정했다. 이 저장소는 `react-hooks` 린트가 엄격해서
**렌더 중 ref 접근**도, **effect 안 동기 setState**도 금지한다. 그래서
캐시 미러링 ref는 별도 effect에서 동기화하고, "마지막 성공 데이터"는 fetch의 `.then`
비동기 콜백에서 갱신했다. 규칙이 "어떻게 짤지"를 절반쯤 결정한 셈이다.

| 상황 | 처음 | 최종 |
|---|---|---|
| 일시적 500 이후 | 새로고침 전까지 "데이터 없음" 고정 | 단위 전환/재시도로 self-heal |
| 서버 에러 표시 | "데이터가 없습니다"(오독) | "불러오지 못했습니다 · 다시 시도" |
| 미캐시 단위 전환 | 빈 박스로 깜빡 | 이전 차트를 흐리게 유지 |
| 상태 구분 | 로딩 / 나머지(2) | 로딩 / 빈 / 에러 / stale(4) |

## 배운 것

- **캐시에 '실패'를 담으려면 수명을 같이 설계해야 한다.** 성공 캐시와 실패 캐시는 수명이 다르다.
  성공은 오래 살아도 되지만 실패는 짧게 살고 다음 기회에 다시 시도돼야 한다.
  만료·재시도 없는 실패 캐시는 일시적 장애를 영구 장애로 바꾼다.
- **로딩·빈·에러는 세 상태다.** 둘로 접으면 장애가 "정상적으로 0건"으로 위장된다.
  사용자에게 "없다"와 "못 불러왔다"는 완전히 다른 말이다.
- **최적화가 회복 경로를 지울 수 있다.** 재조회로 스스로 낫던 화면을 캐시가 굳혔다.
  캐시를 넣을 때는 "실패했을 때 어떻게 다시 시도되는가"를 같이 넣어야 한다.
- **프레임워크 제약이 구현을 정한다.** 렌더 중 ref 금지·effect 내 setState 금지 같은 규칙은
  우회가 아니라 설계 신호로 받아들이는 편이 결과가 깔끔했다.
